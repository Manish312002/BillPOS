## 1. Executive Summary & Design Principles

This document provides the formal relational database schema design, Prisma schema DSL specifications, foreign-key constraint rules, indexing strategies, BigInt financial serialization standards, and transaction concurrency definitions for BillingBuddy's **Subscription & Entitlements** module.

### Core Database Invariants:
1. **Four-Tier Financial Architecture (Clarification B):**
   - **Tier 1 (Database Persistence):** PostgreSQL `BIGINT` mapped to Prisma `BigInt`.
   - **Tier 2 (Application Calculation):** Native JavaScript `BigInt` (`99900n`) and integer paise arithmetic via `@billingbuddy/shared`. Zero floating-point math.
   - **Tier 3 (External API Wire Representation):** Canonical **decimal integer strings** (e.g., `"amountPaise": "99900"`).
   - **Tier 4 (Human-Readable UI Presentation):** Localized currency strings (e.g., `"amountFormatted": "₹999.00"`).
2. **Historical Subscription Preservation via Partial Unique Index:**
   Enforces at most *one current/active subscription* per tenant via PostgreSQL Partial Unique Index while permitting unlimited historical (`CANCELED`, `EXPIRED`) records.
3. **Hardware-Backed Device Identity:** `PosDevice` records store `publicKeyPem` and `publicKeyThumbprint` generated by the device's Android Keystore.
4. **Immutability of Invoices & Payments:** Paid invoices and verified payments cannot be mutated or deleted.
5. **Referential Safety (`ON DELETE RESTRICT`):** Commercial plans, active subscriptions, and financial records cannot be deleted if referenced by foreign keys.

## 4. BigInt & Decimal Integer String Architecture (Clarification B)

### 4.1 Four-Tier Representation Framework

| Tier | Environment | Data Type | Example Value | Serialization / Handling Rule |
|---|---|---|---|---|
| **Tier 1: Persistence** | PostgreSQL / Prisma | SQL `BIGINT` / JS `BigInt` | `99900n` | Native 64-bit signed integer. Zero decimals. |
| **Tier 2: Calculation** | Backend Runtime | JavaScript `BigInt` | `BigInt(99900)` | Strict integer arithmetic via `@billingbuddy/shared/src/utils/currency.js`. Zero float math. |
| **Tier 3: API Wire** | REST JSON Payloads | **Decimal Integer String** | `"99900"` | Canonical JSON string format. Eliminates IEEE 754 precision loss across all clients. |
| **Tier 4: Display** | React Frontend / POS | Formatted String | `"₹999.00"` | Generated via `formatINR(paiseString)`. For presentation only. |

### 4.2 Zod API Validation Specification
All incoming API payloads containing monetary values validate decimal integer strings:

```javascript
export const decimalIntegerPaiseSchema = z.string()
  .regex(/^\d+$/, 'Must be a valid decimal integer string representing paise')
  .refine(val => {
    try {
      const b = BigInt(val);
      return b >= 0n && b <= 100_000_000_000_000n; // Up to ₹1 trillion paise
    } catch {
      return false;
    }
  }, 'Paise amount out of allowable range')
  .transform(val => BigInt(val));
```

### 4.3 Explicit API DTO Serialization (Zero Global Prototype Mutation)
To avoid modifying the global `BigInt.prototype` (preventing prototype pollution, cross-library collisions, and hidden serialization behavior), all controller and service boundaries use explicit DTO transformer functions. These transformers explicitly serialize Prisma `BigInt` fields to canonical decimal integer strings and localized formatted strings before emitting JSON responses:

```javascript
// packages/shared/src/dto/subscription.dto.js
import { formatINR } from '../utils/currency.js';

export function formatPaiseDto(amountPaise) {
  if (amountPaise === null || amountPaise === undefined) return null;
  const stringValue = typeof amountPaise === 'bigint' ? amountPaise.toString() : String(amountPaise);
  return {
    amountPaise: stringValue,
    amountFormatted: formatINR(stringValue)
  };
}

export function toPlanPriceDto(planPrice) {
  return {
    id: planPrice.id,
    billingCycle: planPrice.billingCycle,
    currency: planPrice.currency,
    ...formatPaiseDto(planPrice.amountPaise),
    isActive: planPrice.isActive
  };
}

export function toSubscriptionInvoiceDto(invoice) {
  return {
    id: invoice.id,
    invoiceNumber: invoice.invoiceNumber,
    subtotal: formatPaiseDto(invoice.subtotalPaise),
    tax: formatPaiseDto(invoice.taxPaise),
    total: formatPaiseDto(invoice.totalPaise),
    paid: formatPaiseDto(invoice.paidPaise),
    status: invoice.status,
    dueDate: invoice.dueDate,
    periodStart: invoice.periodStart,
    periodEnd: invoice.periodEnd
  };
}
```

## 5. PostgreSQL Partial Unique Index & History Preservation

To support Decision D-02 (one active subscription per tenant) while enabling infinite historical records (`CANCELED`, `EXPIRED`), the migration script deploys:

```sql
CREATE UNIQUE INDEX "idx_tenant_subscriptions_single_active" 
ON "TenantSubscription" ("tenantId") 
WHERE "status" IN ('TRIAL', 'ACTIVE', 'GRACE_PERIOD', 'READ_ONLY', 'SUSPENDED');
```

When a subscription is canceled or superseded, its status is set to `CANCELED` or `EXPIRED`. This immediately removes it from the partial index predicate, enabling the creation of a new active subscription row without losing historical audits or pricing terms.
