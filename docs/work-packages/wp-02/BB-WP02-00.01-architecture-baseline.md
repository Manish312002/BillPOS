## 3. Security Test Matrix

| Test Scenario | Vector / Input | Expected System Behavior | Work Package Microtask |
|---|---|---|:---:|
| **Invalid Password** | Incorrect password on login | 401 Unauthorized; uniform generic error message | 02.03, 02.06 |
| **Superadmin OTP Expiry** | OTP submitted after 5 minutes | 400 Bad Request (`OTP_EXPIRED`); rejection | 02.03 |
| **Superadmin OTP Replay** | Re-submitting already consumed OTP | 400 Bad Request (`OTP_ALREADY_USED`) | 02.03 |
| **OTP Brute-Force** | 4 invalid OTP attempts | Lock challenge after 3 attempts (`MAX_ATTEMPTS_EXCEEDED`) | 02.03, 02.05 |
| **OTP Resend Invalidation** | Requesting new OTP | Marks previous OTP as invalid; previous OTP cannot be used | 02.03, 02.04 |
| **Concurrent OTP Attempts** | Parallel requests with same OTP | Database row locking or atomic update prevents dual use | 02.03, 02.05 |
| **Invitation Token Expiry**| Activation attempted after 12h | 400 Bad Request (`INVITATION_EXPIRED`) | 02.05 |
| **Invitation Token Replay**| Activating an accepted token | 400 Bad Request (`INVITATION_ALREADY_ACCEPTED`) | 02.05 |
| **Superadmin Route Tamper**| Owner attempting `/platform/*` | 403 Forbidden; zero platform leakage | 02.03, 02.06 |
| **Cross-Tenant IDOR** | Owner querying different `tenantId` | Scoped by server `req.tenantId`; returns 404/403 | 02.06, 02.07 |
| **Onboarding Bypass** | Incomplete store accessing POS | `OnboardingGuard` intercepts and redirects to step wizard | 02.07 |
| **Session Fixation** | Login with pre-existing cookie | New cryptographic session token minted upon auth | 02.03, 02.06 |
| **Session Revocation** | Calling `POST /api/auth/logout` | Session deleted in DB; cookie cleared immediately | 02.03, 02.06 |
| **Secrets Exposure** | Examining API responses & logs | Passwords, hashes, OTPs, session secrets redacted | 02.01–02.07 |

## 4. Confirmed Architecture Decisions

1. **Stack Adherence:** Express 5, React 19 JSX, Tailwind CSS v4, Redux Toolkit, Axios, Prisma 6.19.3, pure ECMAScript Modules.
2. **Language Boundary:** Strictly 0 TypeScript (`.ts`/`.tsx`).
3. **Session Type:** Opaque server-side sessions stored in PostgreSQL and delivered via `httpOnly`, `Secure`, `SameSite=Lax` cookies. (Zero `localStorage` tokens).
4. **Password Hashing:** Native `bcrypt` with cost factor 12. Prohibiting `bcryptjs`.
5. **Two-Factor Gate:** Superadmin access strictly gated by WhatsApp OTP verification before granting dashboard tokens.
6. **Owner Activation:** 12-hour expiry link + WhatsApp OTP verification + self-selected password. Superadmin never sees Owner password.
7. **Single Frontend Monorepo:** Both portals reside in `apps/web`, with isolated `/platform/*` and `/owner/*` namespaces.
8. **Email Verification:** Architectural hooks preserved (`User.emailVerified`), but active sending remains disabled in this phase.

## 5. Decisions Requiring Human Approval

Before proceeding with implementation in Microtask 02.01, the following security defaults require human sign-off:

1. **OTP Validity Duration:** Proposed default is **5 minutes (300s)**. (Is this acceptable, or is a shorter/longer window required?).
2. **OTP Maximum Verification Attempts:** Proposed default is **3 attempts** before the challenge is permanently invalidated.
3. **OTP Resend Cooldown:** Proposed default is **60 seconds** cooldown between resend requests.
4. **Session Idle Timeout & Rolling Window:** Proposed default is **7 days** active session validity with rolling `lastSeenAt` update.
5. **Root Superadmin Initial Password:** Shall the initial root Superadmin (`+918380989776`) password be provisioned via a secure environment variable `ROOT_SUPERADMIN_INITIAL_PASSWORD` during database seeding?

## 6. Architecture Risks & Mitigations

1. **Risk:** WhatsApp API delivery latency or upstream outage during Superadmin login.
   - **Mitigation:** Implement a clear countdown timer in the UI, resend button after 60s, and a fallback logging/webhook mechanism in non-production environments (`WhatsAppProviderMock`).
2. **Risk:** Floating-point currency or financial data drift in future steps.
   - **Mitigation:** Reinforce integer paise math established in `@billingbuddy/shared/utils/currency.js`.
3. **Risk:** Cross-Tenant Data Leakage (IDOR).
   - **Mitigation:** Zero client-supplied `tenantId` trust. The API middleware resolves `activeTenantId` from the verified session record and attaches `req.tenantId` for all downstream controller queries.
