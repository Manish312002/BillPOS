## 6. Backend Architecture Findings

1. **Express 5 Application Architecture (`apps/api/src/app.js`):**
   - Factory pattern via `createApp()`, exporting both `app` and `createApp` for testability without port collisions.
   - Native promise rejection handling (Express 5 core capability).
   - Middleware ordering strictly enforced:
     1. `cors()` with origin sanitization and credentials support.
     2. `express.json()` and `express.urlencoded({ extended: true })`.
     3. Structured JSON request logger (`middleware/requestLogger.js`).
     4. Base ping endpoint (`GET /`).
     5. Scoped API router (`app.use(env.API_PREFIX, apiRouter)`).
     6. Catch-all RFC 7807 404 handler (`middleware/notFoundHandler.js`).
     7. Centralized error handling middleware with stack sanitization (`middleware/errorHandler.js`).
2. **Environment Validation (`src/config/env.js`):**
   - Strict Zod parsing on startup with fail-fast process termination on invalid configurations.
3. **Database Foundation (`src/db/client.js` & `prisma/schema.prisma`):**
   - Singleton client pattern preventing connection pool exhaustion.
   - Pinned Prisma 6.19.3 (avoiding Prisma 7's breaking TypeScript configuration requirements).
   - Validated PostgreSQL datasource baseline without premature data models.
4. **Health Endpoints (`src/routes/health.routes.js` & `src/services/health.service.js`):**
   - Implements structured uptime, memory metrics, timestamp, and database connectivity probe.

## 11. Inconsistencies & Findings Reconciled

### Discrepancy 1: Vite Version Documentation (`v8.0.1` vs `8.3.6`)
- **Evidence:** The 01.08 report text contained a snippet showing `vite v8.0.1`.
- **Finding:** Inspection of `node_modules/vite/package.json`, `package-lock.json`, and direct invocation of `npm run build` confirmed the installed, locked, and executing version is strictly **Vite 8.3.6**. The reference to `v8.0.1` in report 01.08 was a manual documentation transcription typo.
- **Severity:** LOW (Documentation Typo).

### Discrepancy 2: Root Route Behavior (`PortalIndexPage` vs `/owner/overview` Redirect)
- **Evidence:** Report 01.08 summarized the root route as `Root redirect (/ -> /owner/overview)`.
- **Finding:** Inspection of `apps/web/src/app/router/index.jsx` (line 28) and `apps/web/tests/frontend.test.jsx` (line 29) proves that `/` renders `PortalIndexPage` (the dual-portal selector). Redirects to `.../overview` occur on `/platform` and `/owner` index routes, not root `/`.
- **Severity:** LOW (Documentation Misdescription).

### Discrepancy 3: Node.js `v22.17.1` Lifecycle Classification
- **Evidence:** Previous reports referred to Node `v22.17.1` as "Active LTS".
- **Finding:** Node.js 22 (Jod) was Active LTS from October 2024 to October 2025, and transitioned into **Maintenance LTS** in October 2025 (scheduled EOL April 2027), while Node.js 24 is the Active LTS line. Labeling `v22.17.1` as "LTS" is accurate regarding its even-numbered LTS channel, but its specific lifecycle state in 2026 is Maintenance LTS.
- **Severity:** INFORMATIONAL (Lifecycle Classification Clarification).

### Discrepancy 4: Shared Package Consumption in Workspaces
- **Evidence:** `@billingbuddy/shared` has complete subpath exports and 13 unit tests, but is not yet imported by `apps/api` or `apps/web`.
- **Finding:** In the WP-01 foundation phase, `@billingbuddy/shared` was built and validated in isolation. Adding `"@billingbuddy/shared": "*"` to `apps/web/package.json` and `apps/api/package.json` was deferred to domain implementation work packages (WP-02 Authentication, WP-03 Store Operations) when domain constants and Zod contracts will be consumed.
- **Severity:** LOW (Expected WP Boundary Separation).

### Discrepancy 5: Earlier Workspace Verification Failure Explained
- **Evidence:** Background task `task-719` showed test failures with `Error: connect EACCES 127.0.0.1:52020`.
- **Finding:** On Windows, the standard execution sandbox restricts local loopback TCP port binding. Because backend health integration tests execute `supertest(app)` (which temporarily binds an ephemeral localhost socket), standard sandboxed execution triggers `EACCES`. Running the suite with authorized network/loopback permissions (`BypassSandbox: true`) succeeded cleanly with 0 errors across all 29 tests.
- **Severity:** RESOLVED / DOCUMENTED (Sandbox Constraint).
