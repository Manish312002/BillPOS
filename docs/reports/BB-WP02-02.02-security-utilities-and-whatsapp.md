## 1. Executive Summary

In strict accordance with the approved **ADR-002** (Zero-Cost Authentication, Superadmin TOTP & Manual WhatsApp Invitations), Microtask **BB-WP02-02.02** implements the offline cryptographic security utilities, standard RFC 6238 TOTP engine, manual WhatsApp Click-to-Chat (`wa.me`) link generator, and shared authentication contracts for BillingBuddy.

All obsolete automated messaging provider abstractions (`WhatsAppProvider.js`, `MockWhatsAppProvider.js`, and external API factory stubs) have been completely removed. In their place, a zero-cost, offline-capable, and telecom-resilient foundation has been established:
1. **RFC 6238 TOTP Engine (`apps/api/src/utils/totp.js`):** Pure Node.js `crypto` implementation supporting Base32 secret generation, standard `otpauth://totp/...` URI formatting, HMAC-SHA1 dynamic truncation verified against all 5 official RFC 6238 Appendix B test vectors, constant-time 6-digit verification with a bounded $\pm 30$-second clock-drift window ($\pm 1$ step), and single-use hashed recovery backup codes.
2. **Manual WhatsApp Click-to-Chat Utility (`apps/api/src/utils/whatsapp.js`):** Formats official `https://wa.me/{digits}?text={encoded}` deep links for manual sharing of owner invitations with international phone normalization, URL encoding, and zero automated dispatch.
3. **Consolidated Security Utilities (`apps/api/src/utils/security.js`):** 256-bit opaque random token generation (`generateOpaqueToken`), SHA-256 token hashing (`hashToken`), native `bcrypt` password hashing and verification with cost factor 12 (`hashPassword`, `verifyPassword`, `validatePasswordPolicy`), and constant-time string equality (`verifyTimingSafe`).
4. **Shared Authentication Contracts (`packages/shared/src/contracts/auth.contracts.js`):** Updated with Zod schemas for TOTP verification, enrollment confirmation, recovery code verification, and bearer-token Owner activation (omitting obsolete WhatsApp OTP requirements).

Across the entire monorepo, all **102 unit and integration tests** pass cleanly (59 backend tests, 30 shared package tests, 13 frontend tests), with 0 ESLint issues, 100% Prettier formatting compliance, and full workspace verification.

## 3. Cryptographic & Security Architecture Decisions

### A. RFC 6238 TOTP Engine
- **Secret Generation:** 20 random bytes (160 bits entropy) encoded in unpadded Base32 (`generateTotpSecret()`), generating a 32-character Base32 secret string matching standard authenticator app requirements.
- **Dynamic Truncation:** Implements RFC 4226 Section 5.3 and RFC 6238:
  ```javascript
  const offset = digest[digest.length - 1] & 0x0f;
  const binary =
    ((digest[offset] & 0x7f) << 24) |
    ((digest[offset + 1] & 0xff) << 16) |
    ((digest[offset + 2] & 0xff) << 8) |
    (digest[offset + 3] & 0xff);
  const otpNumber = binary % 1000000;
  ```
- **Known Test Vectors:** Validated against all 5 official RFC 6238 Appendix B test vectors for HMAC-SHA1 at Time = 59s (`287082`), 1111111109s (`081804`), 1111111111s (`050471`), 1234567890s (`005924`), and 2000000000s (`279037`).
- **Clock Drift Tolerance:** Verifies codes across a bounded $\pm 1$ time-step window ($[-30\text{s}, +30\text{s}]$) using constant-time comparison (`crypto.timingSafeEqual`).
- **Emergency Recovery Codes (SEC-01: 128-bit Entropy):** Generates 8 cryptographically random formatted codes using `crypto.randomBytes(16)` ($16 \text{ bytes} \times 8 = 128\text{ bits}$ of entropy), formatted as 4 hyphenated blocks of 8 hex characters (`XXXXXXXX-XXXXXXXX-XXXXXXXX-XXXXXXXX`). Stored strictly as SHA-256 hashes of the normalized 32-character string.

### B. TOTP Secret Encryption at Rest (SEC-02: Authenticated AES-256-GCM)
- **Algorithm:** Authenticated AES-256-GCM (`aes-256-gcm`).
- **Key Validation:** Strictly requires an independently configured 32-byte key (`TOTP_ENCRYPTION_KEY`) in Buffer, 64-character hex, or 32-character UTF-8 format. Weak, short, or malformed keys are explicitly rejected without silent key derivation.
- **Fresh IV:** Every encryption generates a fresh 12-byte cryptographically random IV (`crypto.randomBytes(12)`).
- **Authentication Tag:** 16-byte GCM authentication tag (`cipher.getAuthTag()`).
- **Versioned Payload Format:** `v1:<iv_24hex>:<tag_32hex>:<ciphertext_hex>`.
- **Validation & Tamper Resistance:** Decryption strictly validates the payload structure, verifying version `v1`, 24-hex IV, 32-hex tag, and valid ciphertext before deciphering. Tampered ciphertext, modified authentication tags, corrupted payloads, or mismatched keys throw safe descriptive errors without exposing cryptographic secrets or keys.

### C. Manual WhatsApp Click-to-Chat (`wa.me`)
- **Phone Normalization:** Converts any phone format (e.g. `+91 83809-89776`, `8380989776`, `+1 (415) 555-2671`) into pure international digits (`918380989776`).
- **URL Encoding:** Encodes all spaces, linebreaks, and special characters via `encodeURIComponent`.
- **Zero Automated Dispatch:** The server never sends outbound WhatsApp messages or calls external APIs. The frontend triggers the deep link solely upon an explicit user click.
- **Zero Credential Exposure:** Message templates strictly omit passwords, session tokens, or internal secrets.

### C. Password & Token Hashing
- **Password Engine:** Native `bcrypt` compiled for Node 22 with cost factor 12 rounds (`$2b$12$...`).
- **Complexity Policy:** Enforced minimum 10 characters, at least 1 uppercase letter, 1 lowercase letter, 1 digit, and 1 special symbol.
- **Opaque Tokens:** 32 bytes (256 bits) of cryptographic entropy formatted as base64url. Plaintext tokens are delivered only to cookies/links; only deterministic SHA-256 hashes are persisted to PostgreSQL.
