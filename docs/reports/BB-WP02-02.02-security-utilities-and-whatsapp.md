## 1. Executive Summary

Microtask **BB-WP02-02.02** establishes the cryptographic security utilities, rate limiting algorithms, WhatsApp delivery provider abstraction, and shared authentication contracts required for BillingBuddy's two-factor authentication and store owner invitation workflows.

All cryptographic functions enforce modern standards:
- 6-digit numeric OTPs generated with cryptographically secure randomness (`crypto.randomInt`).
- Keyed HMAC-SHA256 digests computed using a dedicated server pepper secret (`OTP_PEPPER_SECRET`).
- Constant-time digest comparison (`crypto.timingSafeEqual`) to prevent timing side-channel attacks.
- Opaque 32-byte random token generation (`generateOpaqueToken`) and SHA-256 token hashing (`hashToken`).
- Sliding-window rate limiting and cooldown policy calculations (5-minute expiry, 3-attempt ceiling, 60-second resend cooldown).
- Provider-agnostic WhatsApp interface with an in-memory `MockWhatsAppProvider` for local development/testing that strictly redacts OTPs from console logs, allows message queue inspection, and supports simulated delivery failures. The factory prevents false delivery reporting if external provider credentials are missing.
- Shared Zod validation contracts in `@billingbuddy/shared` covering all login, verification, tenant creation, and activation schemas.

## 3. Cryptographic & Security Architecture Decisions

### A. 6-Digit Numeric OTP Generation
- **Implementation:** `crypto.randomInt(100000, 1000000).toString()`
- **Properties:** Uniform distribution across $[100000, 999999]$, providing exactly 6 numerical digits with zero modulo bias.

### B. Keyed HMAC-SHA256 OTP Digest
- **Implementation:** `crypto.createHmac('sha256', pepper).update(otp).digest('hex')`
- **Protection:** Protects against precomputed rainbow table attacks on the $10^6$ search space. The pepper secret (`OTP_PEPPER_SECRET`) is stored outside the database in the environment.

### C. Timing-Safe Digest Comparison
- **Implementation:** `crypto.timingSafeEqual(computedBuffer, storedBuffer)`
- **Protection:** Eliminates timing side-channel attacks by evaluating character comparison in constant time regardless of where a mismatch occurs.

### D. Opaque Tokens & Storage Hashing
- **Generation:** `crypto.randomBytes(32).toString('base64url')` (256 bits of entropy).
- **Storage Hash:** `crypto.createHash('sha256').update(token).digest('hex')`
- **Protection:** Plaintext session and invitation tokens delivered to cookies/links are never stored in the database. Only SHA-256 hashes are persisted.

### E. Policy Timestamps & Sliding Window Limiter
- **Expiry Window:** $T + 300\text{s}$ (5 minutes).
- **Attempt Ceiling:** Maximum 3 attempts per challenge.
- **Resend Cooldown:** $T + 60\text{s}$ (60 seconds).
- **`RateLimiter`:** In-memory sliding-window tracker providing fast rejection of abusive requests before querying PostgreSQL.

## 4. WhatsApp Provider Abstraction

### Interface Contract:
- `sendOtpMessage({ destination, otp, purpose, expiryMinutes })`
- `sendInvitationMessage({ destination, storeName, invitationLink, otp, expiryHours })`

### Mock Implementation (`MockWhatsAppProvider`):
- Safely logs delivery metadata without plain text OTPs:
  `[MockWhatsApp] Dispatched OTP to +918380989776 (Purpose: SUPERADMIN_LOGIN, MessageId: mock_wa_...)`
- Maintains in-memory queue for test assertions (`getSentMessages()`, `getLastMessageFor()`, `clearMessages()`).
- Supports controlled failure simulation (`simulateFailureNext(error)`) to test upstream provider outages.

### Factory & Configuration Boundary (`getWhatsAppProvider`):
- Returns `MockWhatsAppProvider` when `WHATSAPP_PROVIDER=mock` (default).
- If external providers (`meta`, `gupshup`, `twilio`) are configured without valid API keys, throws an informative error:
  `[WhatsApp Configuration Error] WhatsApp provider "..." is configured, but required credentials (WHATSAPP_API_KEY) are missing. Cannot simulate delivery without valid provider configuration.`
